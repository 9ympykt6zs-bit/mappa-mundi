## Handoff — specialist completes

Audit completed (read-only). The reusable fault boundary is the Guided child launch contract, rather than the physical source geometry:

- `createPhysicalFeatureBlocks()` starts each feature with `destination.targetIds: [feature.targetId]` (`src/guided-learning-orchestration.js`). `createDynamicPhysicalIntroductionBlock()` can widen an introduction to the selected cohort's introduced/new members, and `createDynamicPhysicalPracticeBlock()` uses `retrievalTargetIds`, but that widening exists only in the live orchestration decision. `rehydrateGuidedLearningChildBlock()` then trusts `child.targetIds` verbatim. A stale or previously single-target child contract therefore reopens a physical child with one target even when the source activity contains the whole family.
- `launchGuidedLearningChildBlock()` passes `block.destination.targetIds` both as `focusTargetIds` and (for retrieval) `memoryTrailTargetIds`. `createMemoryTrailSession()` filters `activity.targets` by that set, then `targetPoolIds` and the checkpoint are built from the filtered result. This is the point at which a one-target contract becomes a one-candidate retrieval session; `chooseMemoryTrailTargetPool()` does not narrow a normal 2–5 member cohort further.
- Initial physical introductions use the full family activity from `getStudyStepContext()` (for example `us-physical-rivers`, `us-physical-lakes`, or a mountain section), so `runner.updateActivity()` normally receives all source activity targets. Synthetic `createGuidedPhysicalReviewActivity()` is used only when `physicalReviewActivity` is true and correctly reconstructs the requested IDs from `sourceActivityIds`. The smallest reusable fix is to make the resolved launch candidate set explicit and authoritative: derive it deterministically from `cohort.supportedMemberTargetIds`, retaining all session members plus already introduced same-family members needed to reach the cohort's preferred/minimum retrieval size; validate/intersect any persisted child subset against that set; use the result for `destination.targetIds`, `memoryTrailTargetIds`, and the checkpoint. Do not infer membership from camera focus or from the source activity's complete target list.
- Camera is intentionally first-target focused today: `resolveGuidedPhysicalFeatureCamera()` and `applyGuidedPhysicalFeatureCamera()` use `activeStudySession.focusTargetIds[0]`; retrieval's persistent cohort camera is supplied separately for mixed/review blocks. Camera bounds should be computed from the candidate set for a multi-member retrieval window (or retain an authored cohort camera where present), while preserving the existing teaching camera/highlight behavior.
- Family source/render paths are distinct but all are fed by `runner.shapeTargets`, which is the current activity's shape targets. Lakes/water bodies render through `target-shapes`/`state-fill` and accept `target-hit-fill`; rivers additionally populate `river-lines` and `river-hit-line` with a wide, near-transparent hit width and a screen-space geometry fallback; mountains populate `mountain-range-corridors` and `mountain-range-symbols` for display, while taps still resolve through `target-hit-fill`/geometry fallback (the generated symbol/corridor layers are not themselves the retrieval hit contract). `getTargetIdsAtMapPoint()` returns rendered IDs, river fallback IDs, and padded/geometry IDs; with a priority target it can prepend that target but should not be changed to hide siblings.
- Neutral retrieval styling is controlled by `setMemoryTrailHighlight([])`, checkpoint pre-answer suppression, and the runner's paint expressions. Prompt highlighting is intentionally absent for `guidedLocatingOnly` name-to-place retrieval; the selected/picked chip must not reveal its target. Feedback later uses the answered target and canonical retrieval result, so the candidate expansion must not add evidence for unprompted siblings. `recordGuidedPhysicalRetrievalResult()` and `recordCanonicalMemoryTrailEvidence()` remain keyed to the current prompt target only.
- Persistence impact is bounded: the launch contract (`guided-child-launch-contract`) and orchestration state's active block/return context persist the candidate IDs; reload rehydrates them. The repair should normalize old one-target contracts at rehydration/launch using the current cohort and introduced state, without rewriting Journey progress, ordinary Memory Trail, teaching progress, scheduler order, or canonical evidence. A completed checkpoint must retain its target order/retry state; only its validated membership may be widened when the persisted contract is incomplete.
